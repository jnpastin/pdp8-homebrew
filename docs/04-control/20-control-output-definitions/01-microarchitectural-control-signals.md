# Microarchitectural Control Signals

## 1. Purpose

Defines the complete set of microarchitectural control signals required to implement the μop catalog.

This document is the authoritative source for:

- signal definitions
- signal semantics
- encoding and constraints
- mapping from control signals to μop behavior

Microarchitectural control signals:

- are generated by the control store via CONTROL_WORD
- directly control datapath behavior
- are internal to the CPU
- are not externally visible

All internal state transformations required by μops must be realizable exclusively through combinations of the microarchitectural control signals defined in this document.

μops that interact with memory, I/O, or external systems additionally require architectural control signals, which are defined separately.

**μops are controlled by the union of control outputs, but this document defines only the subset responsible for internal state changes.**

No datapath behavior may exist outside of this defined signal set.

---

## 2. Design Principles

Microarchitectural control signals are defined to provide a complete, deterministic, and minimal representation of all internal datapath behavior required by the μop catalog.

---

### 2.1 Completeness

The signal set must be sufficient to implement all internal state transformations required by μops.

Constraint:

- All internal state updates defined by μops must be expressible using combinations of these signals.

---

### 2.2 Exclusivity

Constraint:

- No internal datapath behavior may occur without explicit control signals.
- No implicit or side-effect-driven state changes are permitted.

---

### 2.3 Determinism

Constraint:

- For a given CONTROL_WORD, the resulting signal values and system behavior must be fully determined.
- No signal may depend on undefined or external side effects.

---

### 2.4 Non-Persistence

Constraint:

- Control signals are evaluated each cycle and do not persist across cycles.
- No signal retains state beyond the cycle in which it is defined.

---

### 2.5 Separation of Concerns

Constraint:

- Microarchitectural control signals define only internal datapath behavior.
- Architectural interactions (e.g., memory or I/O) are controlled by separate architectural signals.
- External systems (e.g., memory, DMA) must not be modeled as part of microarchitectural control.

---

### 2.6 Explicit Activation

Constraint:

- All state-changing operations must be explicitly enabled.
- The presence of valid select signals alone must not produce any effect.

---

### 2.7 Valid Encoding

Constraint:

- All control signals must have valid encodings in every cycle.
- Undefined or reserved encodings must not be used.

---

### 2.8 Arbitration Safety

Constraint:

- External arbitration mechanisms (e.g., DMA) may suppress the effects of control signals.
- Suppression must not alter the definition or interpretation of the CONTROL_WORD.

---

## 3. Signal Classes

Microarchitectural control signals are interpreted according to their functional role.

Signal classes define how signals contribute to datapath behavior and how they interact to produce state transitions.

---

### 3.1 Enable Signals

Enable signals determine whether an operation occurs.

Properties:

- single-bit  
- active-high  
- control state updates or datapath actions  

Behavior:

```
if ENABLE = 1:
    operation is committed at TP
else:
    no operation occurs
```

Constraints:

- No state change may occur unless explicitly enabled  
- Multiple enable signals targeting the same destination must not be asserted simultaneously  
- Enable signals must not imply data selection or operation type  
- Enable signals affecting state updates must be suppressed when `DMA_HOLD = 1`  

---

### 3.2 Select Signals

Select signals define the parameters of an operation.

These include:

- data source selection  
- ALU operand selection  
- operation selection  

Properties:

- multi-bit encoded fields  
- must always contain a valid encoding  

Behavior:

- Select signals determine values and operations  
- They have no effect unless used by an enabled operation  

Constraints:

- Select signals must always contain a valid encoding  
- Select signals must not produce any effect without an associated enable signal  
- Invalid or reserved encodings must not be used  

---

### 3.3 Data Value Signals

Data value signals provide concrete data values that are consumed by the datapath.

These signals represent values, not control decisions.

They may originate from:

- constants defined within the CPU (e.g., `CONST_0`, `CONST_1`)  
- externally supplied data (e.g., memory data input, I/O data input)  

Properties:

- represent data values, not control decisions  
- do not control or initiate operations  
- have no effect unless selected and consumed by an enabled operation  

Behavior:

- Data value signals supply inputs to datapath elements  
- Their values are selected via select signals and committed via enable signals  

Constraints:

- Data value signals must always represent valid values within their defined domain  
- Data value signals must not produce side effects on the system  
- Data value signals must not bypass select signal interpretation  
- Data value signals only influence system behavior when:
  - selected by a select signal, and  
  - committed by an enable signal  

---

### 3.4 Interaction Model

Operations are defined by coordinated use of all signal classes.

```
value = data_value_signal or selected datapath source
result = f(select signals, value)

if ENABLE:
    commit result at TP
```

Implications:

- Data Value Signals provide input values  
- Select Signals determine how values are used  
- Enable Signals determine whether results are committed  

All three signal classes are required for meaningful behavior.

---

### 3.5 Inactive Behavior

When an operation is not enabled:

- Select signals must still contain valid encodings  
- Data value signals must still present valid values  
- No state change occurs  
- No implicit behavior is permitted  

Constraint:

- All signals must be defined every cycle, regardless of relevance  

---

### 3.6 Deterministic Interpretation

Constraint:

- Control signal interpretation must be fully deterministic  
- No signal may introduce implicit, context-dependent, or externally derived behavior beyond defined inputs  

---

### CONST_0

**Mnemonic:** CONST_0  
**Name:** Constant Zero  
**Class:** Data Value  
**Bit Width:** 1 (control), 12-bit value  

**Purpose:** Direct zero injection for non-ALU register writes.

**Encoding:**
```
0 → disabled
1 → enabled (000000000000)
```

**Constraints:**
- Must not be used as ALU operand
- Used only for direct register load paths

### IDB_DRIVE

**Mnemonic:** IDB_DRIVE  
**Name:** Internal Data Bus Drive Enable  
**Class:** Enable  
**Bit Width:** 1  

**Purpose:** Enables the selected source to drive the internal datapath bus (IDB).

**Encoding:**
```
0 → no drive
1 → drive IDB
```

**Constraints:**
- Must be asserted when IDB_SRC is used  
- Only one source may drive the IDB per cycle  
- Masked by DMA_HOLD  

**Used by μops:**
- [AC_TO_MB](../03-microarchitecture/02-micro-operations.md#ac_to_mb)
- [PC_TO_MB](../03-microarchitecture/02-micro-operations.md#pc_to_mb)

- Must be valid every cycle  
- When PC_LOAD = 1:
  - selected source must be fully driven and valid  
- Not used for constant loads (e.g., PC_SET_1 uses CONST_1 path)  

**Used by μops:**
- [PC_LOAD_EA_ADDR](../03-microarchitecture/02-micro-operations.md#pc_load_ea_addr)

---

## 6. Global Signal Constraints

This section defines invariants that govern all control signal behavior.  
These rules apply to every cycle and must be satisfied by all valid control words.

---

### 6.1 Signal Validity

For every cycle:

- All signals must have defined values  
- All Select signals must contain valid encodings  
- No signal may assume an implicit or undefined state  

Constraint:

```
∀ signal S:
    S ∈ valid_encoding(S)
```

---

### 6.2 Enable Signal Behavior

Enable signals control whether state updates occur.

Constraint:

```
If ENABLE = 0:
    no state change occurs
```

Additional constraints:

- Enable signals must not imply data selection  
- Enable signals must not imply computation  
- Enable signals only gate commit behavior  

---

### 6.3 Select Signal Behavior

Select signals determine:

- data source selection  
- operation selection  

Constraints:

- Select signals must always contain valid encodings  
- Select signals must not produce side effects  
- Select signals have no effect unless paired with an enabled operation  

---

### 6.4 Data Value Signal Behavior

Data Value signals provide input values.

These include:

- CONST_0  
- CONST_1  
- MDB_INPUT  
- DB_INPUT  

Constraints:

- Data Value signals must always represent valid values  
- Data Value signals must not produce side effects  
- Data Value signals must not be used as ALU operands  
- Data Value signals only affect behavior when consumed by:
  - a destination input path, and  
  - an active enable signal  

---

### 6.5 IDB (Internal Data Bus) Constraints

The IDB is an internal datapath transport mechanism.

Constraints:

```
At most one source may drive the IDB per cycle
```

```
If IDB_DRIVE = 1:
    exactly one IDB_SRC must be selected
```

```
If IDB_SRC is used:
    IDB_DRIVE must be 1
```

Additional constraints:

- No contention is permitted  
- IDB is not architecturally visible  

---

### 6.6 Register Input Exclusivity

Each register must receive input from exactly one source when loaded.

Constraint:

```
For any register R:
    If R_LOAD = 1:
        exactly one input source driving R must be active
```

Examples of input sources:

- IDB path  
- ALU output  
- constant injection (CONST_0, CONST_1)  
- MDB input (for MB only)  

No two sources may drive the same register simultaneously.

---

### 6.7 ALU Operation Constraints

The ALU is a combinational unit that always produces a result.

Constraints:

- ALU_OP must always contain a valid encoding  
- ALU inputs must always be valid  
- ALU outputs have no effect unless captured by a load signal  

```
If no LOAD signal captures ALU output:
    ALU_RESULT is ignored
```

Additional constraints:

- ALU operations must conform to operand requirements  
  - unary operations must use ALU_B_SRC = NONE  
- ALU does not require a NOP operation  

---

### 6.8 Constant Usage Constraints

Constants are used only for direct value injection.

Constraints:

- CONST_0 and CONST_1 must not be routed through ALU operands  
- Constants must not be selected via IDB_SRC  
- Constants may only be used for direct register load paths  

---

### 6.9 Control Signal Exclusivity

Certain signals are mutually exclusive.

Constraints:

```
PC_LOAD and PC_INC must not both be asserted
```

Additional exclusivity constraints must hold wherever two signals:

- target the same destination  
- or define incompatible operations  

---

### 6.10 Bus Domain Isolation

Three data domains exist:

- IDB (internal datapath)  
- MDB (memory interface)  
- DB (I/O interface)  

Constraints:

- IDB, MDB, and DB must not be electrically or logically conflated  
- Signals controlling one domain must not affect another domain  
- Transfers between domains must occur only through defined boundary registers  

---

### 6.11 Determinism Requirement

System behavior must be deterministic.

Constraint:

```
Given a control word:
    resulting state transition is fully determined
```

This implies:

- no implicit behavior  
- no unspecified interactions  
- no dependence on previous signal values unless explicitly encoded  

---

### 6.12 No-Implied-Behavior Rule

No signal may introduce behavior not explicitly defined.

Constraints:

- No signal may imply:
  - data source  
  - operation  
  - side effect  

- All behavior must be the result of:
  - explicit select signals, and  
  - explicit enable signals  

---

### 6.13 Completeness Requirement

Every control cycle must be fully specified.

Constraint:

```
Every signal has a valid value in every cycle,
regardless of whether it is used.
```

---

### 6.14 Invalid Configuration

Any control word that violates these constraints is invalid.

Invalid conditions include:

- multiple IDB drivers  
- multiple input sources for a loaded register  
- invalid select encodings  
- conflicting enable signals  

Behavior of invalid configurations is undefined and must not occur.

---

## 7. Datapath Interaction Model

This section defines how control signals interact with the datapath to produce state transitions.

The model describes the evaluation and commit behavior within a single control cycle.

---

### 7.1 Overview

Each control cycle proceeds through three phases:

```
1. Source Availability
2. Combinational Evaluation
3. State Commit
```

Each phase is required and occurs every cycle.

---

### 7.2 Source Availability

At the start of each cycle:

- All register outputs are available  
- All Data Value signals present valid values  
- External inputs (MDB_INPUT, DB_INPUT) are stable if used  

Sources include:

- Register outputs (AC, MB, PC, etc.)
- ALU output (computed within the cycle)
- Data Value signals (CONST_0, CONST_1, MDB_INPUT, DB_INPUT)

Constraint:

```
All sources must be valid before combinational evaluation begins.
```

---

### 7.3 Combinational Evaluation

During the cycle, combinational logic computes candidate values.

This includes:

#### 7.3.1 ALU Evaluation

```
ALU_RESULT = f(ALU_OP, ALU_A_SRC, ALU_B_SRC)
```

Properties:

- ALU is always active  
- ALU_RESULT is always defined  
- ALU_RESULT may be unused  

---

#### 7.3.2 IDB Evaluation

If IDB_DRIVE = 1:

```
IDB_VALUE = selected source(IDB_SRC)
```

Properties:

- Exactly one source drives IDB  
- IDB is undefined if no source is selected while IDB_DRIVE = 1 (invalid state)  

---

#### 7.3.3 Specialized Functional Units

Certain operations are performed by dedicated combinational units.

Example:

```
EA_FORMED = f(IR, PC, IR.P)
```

Properties:

- Units operate continuously  
- Outputs are always available  
- Selected via Select signals  

---

### 7.4 Input Selection

Each destination register has an input selection mechanism.

Example:

```
MA_INPUT =
    case:
        IDB path
        constant path
```

General form:

```
R_INPUT = selected source according to select signals
```

Constraint:

```
If R_LOAD = 1:
    exactly one input source must be active
```

---

### 7.5 State Commit

At transfer phase (TP):

```
If R_LOAD = 1:
    R ← R_INPUT
```

Properties:

- All register updates occur simultaneously  
- Enable signals gate state changes  
- No intermediate or partial updates occur  

---

### 7.6 Non-Committed Results

If a computed value is not captured:

```
Value is discarded
```

This applies to:

- ALU_RESULT (if not loaded)  
- IDB (if no register loads from it)  
- functional unit outputs (if not selected)  

---

### 7.7 Execution Order Summary

Within a cycle:

```
1. Sources are available
2. Combinational logic computes intermediate values
3. Select signals determine input paths
4. Enable signals commit results at TP
```

This can be expressed as:

```
value = f(select signals, sources)

if ENABLE:
    commit(value)
```

---

### 7.8 Independence of Signal Classes

Signal classes contribute independently:

- Data Value → provides raw values  
- Select → determines how values are used  
- Enable → determines whether results are committed  

No class implies behavior of another.

---

### 7.9 No Implicit Behavior

All datapath activity must be explicitly controlled.

Constraints:

- No register updates occur without an enable signal  
- No value is selected without a select signal  
- No operation occurs implicitly due to data presence  

---

### 7.10 Deterministic Evaluation

Given a control word:

```
All intermediate values and final state transitions are deterministic
```

This requires:

- valid signal encodings  
- no contention on IDB  
- single active source per destination  

---

### 7.11 Domain Interaction

Data moves between domains only through defined paths:

```
MDB → MB          (memory read)
MB → MDB          (memory write)
IDB → registers   (internal transfers)
```

Constraints:

- IDB does not directly connect to MDB or DB  
- All domain crossings occur through designated registers  

---

### 7.12 Invalid States

The following conditions produce undefined behavior:

- multiple IDB drivers  
- multiple input sources to a loaded register  
- invalid select encoding  
- missing required enable/select combinations  

These must not occur.

---

## 8. Bus Interaction Constraints

This section defines the constraints governing how control signals interact with the system’s data transport domains.

The domains themselves are defined elsewhere; this section specifies how they may be used and combined during execution.

---

### 8.1 Domain Isolation

Each data domain must remain logically independent during all control cycles.

Constraints:

- No control signal may implicitly connect two domains  
- Data transfer between domains must occur only through defined boundary registers  
- No signal may cause data to bypass a boundary register  

---

### 8.2 IDB Usage Constraints

IDB is used for internal datapath transfers.

Constraints:

```
At most one source may drive IDB per cycle
```

```
If IDB_DRIVE = 1:
    exactly one IDB_SRC must be selected
```

```
If IDB_SRC selects a source:
    IDB_DRIVE must be 1
```

Additional constraints:

- IDB must not be used for memory transfers  
- IDB must not be used for I/O transfers  

---

### 8.3 MDB Interaction Constraints

MDB is used exclusively for memory transfers through MB.

Constraints:

```
Memory read:
    MDB_INPUT → MB

Memory write:
    MB → MDB
```

Additional constraints:

- No register other than MB may directly access MDB  
- MDB must not be driven by IDB  
- MDB must not source IDB directly  

---

### 8.4 DB (I/O) Interaction Constraints

DB is used exclusively for external I/O interaction.

Constraints:

- DB may only enter the datapath through defined input signals (e.g., DB_INPUT)  
- DB must not be used for internal datapath transfers  
- DB must not be conflated with MDB or IDB  

---

### 8.5 Boundary Enforcement

All domain crossings must be explicit.

Constraint:

```
For any data transfer between domains:
    transfer must pass through a defined boundary register
```

Examples:

```
MDB ↔ MB
DB  → datapath (via explicit input path)
```

Prohibited:

```
IDB → MDB
MDB → IDB (without MB)
DB  → MDB
MDB → DB
```

---

### 8.6 Register Input Consistency Across Domains

When a register is loaded, its input must originate from exactly one domain.

Constraint:

```
If R_LOAD = 1:
    exactly one of the following must be active:
        - IDB path
        - ALU output
        - constant injection
        - MDB input (if applicable)
```

No mixing of domains is permitted within a single load.

---

### 8.7 Concurrent Domain Activity

Different domains may operate simultaneously within a cycle, provided they do not interfere.

Allowed:

```
IDB transfer occurring while memory read occurs on MDB
```

Required constraints:

- No shared drivers between domains  
- No signal may couple timing between domains implicitly  

---

### 8.8 Domain Determinism

All domain interactions must be fully specified by control signals.

Constraint:

```
Given a control word:
    all domain interactions are explicitly determined
```

This prohibits:

- implicit routing  
- inferred connections  
- automatic forwarding  

---

### 8.9 Invalid Domain Configurations

The following conditions are invalid:

- multiple IDB drivers  
- simultaneous conflicting sources to a single register  
- attempting to route IDB traffic onto MDB or DB  
- attempting to bypass boundary registers  

Behavior under these conditions is undefined and must not occur.

---

## 9. Control Signal Interaction Rules

This section defines constraints governing how control signals may be combined within a control word.

These rules ensure that signal interactions are valid, non-conflicting, and deterministic.

---

### 9.1 General Rule

All control signals must combine to produce a valid, unambiguous datapath configuration.

Constraint:

```
A control word must not produce:
    - multiple drivers for a single destination
    - undefined signal combinations
    - conflicting operations
```

---

### 9.2 Enable Signal Exclusivity

Certain enable signals target the same destination or represent incompatible operations.

These must not be asserted simultaneously.

#### 9.2.1 Program Counter

Constraint:

```
PC_LOAD and PC_INC must not both be asserted
```

**Used by μops:**
- [PC_LOAD_EA_ADDR](../03-microarchitecture/02-micro-operations.md#pc_load_ea_addr)
- [PC_SET_1](../03-microarchitecture/02-micro-operations.md#pc_set_1)
- [PC_INC](../03-microarchitecture/02-micro-operations.md#pc_inc)

---

### 9.3 Register Source Exclusivity

When a register is loaded, only one input source may be active.

Constraint:

```
If R_LOAD = 1:
    exactly one input source must drive R
```

Applies to:

- AC, MB, MA, PC, EA, IR, MQ, L

Invalid combinations include:

```
IDB + CONST
IDB + MDB
ALU + CONST
```

---

### 9.4 IDB Signal Dependency

IDB control signals are interdependent.

Constraints:

```
If IDB_DRIVE = 1:
    IDB_SRC must be valid
```

```
If IDB_SRC selects a source:
    IDB_DRIVE must be 1
```

Invalid configurations:

```
IDB_DRIVE = 1 with no valid source
IDB_SRC selected with IDB_DRIVE = 0
multiple conceptual sources active
```

**Used by μops:**
- [AC_TO_MB](../03-microarchitecture/02-micro-operations.md#ac_to_mb)
- [PC_TO_MB](../03-microarchitecture/02-micro-operations.md#pc_to_mb)
- [MB_TO_EA](../03-microarchitecture/02-micro-operations.md#mb_to_ea)
- [MB_TO_IR](../03-microarchitecture/02-micro-operations.md#mb_to_ir)
- [AC_TO_MQ_AND_CLEAR_AC](../03-microarchitecture/02-micro-operations.md#ac_to_mq_and_clear_ac)

---

### 9.5 ALU Operand Requirements

ALU operations impose constraints on operand selection.

#### 9.5.1 Unary Operations

For unary operations:

```
ALU_OP ∈ {NOT, INC, CLEAR, ROR, ROL, RTR, RTL, BSW}
```

Constraints:

```
ALU_B_SRC = NONE
```

Additional constraints:

- Operation is applied to ALU_A_SRC  
- Rotate operations may internally use L as a state element  
- No independently selected second operand is consumed  

**Used by μops:**
- [AC_COMP](../03-microarchitecture/02-micro-operations.md#ac_comp)
- [AC_INC](../03-microarchitecture/02-micro-operations.md#ac_inc)
- [AC_CLEAR](../03-microarchitecture/02-micro-operations.md#ac_clear)
- [AC_ROR](../03-microarchitecture/02-micro-operations.md#ac_ror)
- [AC_ROL](../03-microarchitecture/02-micro-operations.md#ac_rol)
- [AC_RTR](../03-microarchitecture/02-micro-operations.md#ac_rtr)
- [AC_RTL](../03-microarchitecture/02-micro-operations.md#ac_rtl)
- [AC_BSW](../03-microarchitecture/02-micro-operations.md#ac_bsw)

---

#### 9.5.2 Binary Operations

For binary operations:

```
ALU_OP ∈ {ADD, AND, OR}
```

Constraint:

```
ALU_B_SRC ≠ NONE
```

**Used by μops:**
- [ADD_AC_MB](../03-microarchitecture/02-micro-operations.md#add_ac_mb)
- [AC_AND_MB](../03-microarchitecture/02-micro-operations.md#ac_and_mb)
- [AC_OR_MQ](../03-microarchitecture/02-micro-operations.md#ac_or_mq)
- [AC_OR_SR](../03-microarchitecture/02-micro-operations.md#ac_or_sr)

---

### 9.6 Constant Usage Constraints

Constants must not conflict with other input mechanisms.

Constraints:

```
If CONST_0 or CONST_1 is enabled:
    no other input source for that register may be active
```

Invalid:

```
CONST_0 + IDB
CONST_1 + ALU
```

Additional constraint:

```
Constants must not be used as ALU operands
```

---

### 9.7 L Register Interaction

L interacts with ALU operations and direct operations.

Constraints:

```
If L_LOAD = 1:
    L_OP must be valid
```

```
If ALU operation produces carry and it is required:
    L_OP = ALU_CARRY
```

```
L_OP = NOP produces no state change
```

**Used by μops:**
- [ADD_AC_MB](../03-microarchitecture/02-micro-operations.md#add_ac_mb)
- [AC_INC](../03-microarchitecture/02-micro-operations.md#ac_inc)
- [L_CLEAR](../03-microarchitecture/02-micro-operations.md#l_clear)
- [L_COMP](../03-microarchitecture/02-micro-operations.md#l_comp)

---

### 9.8 Domain Exclusivity at Register Input

A register must not mix sources from different domains.

Constraint:

```
If R_LOAD = 1:
    input must come from exactly one domain:
        IDB
        ALU
        MDB
        CONST
```

Invalid:

```
IDB + MDB
ALU + CONST
MDB + CONST
```

---

### 9.9 Select Signal Validity

All select signals must contain valid encodings.

Constraint:

```
Select ∈ valid_encoding
```

Invalid:

```
reserved encodings
undefined values
```

---

### 9.10 No Implicit Dependencies

No signal may imply another signal.

Constraints:

```
IDB_SRC does not imply IDB_DRIVE
IDB_DRIVE does not imply IDB_SRC value
ALU_OP does not imply operand values
```

All dependencies must be explicitly satisfied.

---

### 9.11 Complete Specification Requirement

Every control word must fully specify all required signals.

Constraint:

```
No required signal may be omitted or left undefined
```

Includes:

- all enables  
- all selects  
- all data value controls  

---

### 9.12 Invalid Control Word

A control word is invalid if it violates any constraint in this section.

Examples:

- multiple IDB drivers  
- conflicting register inputs  
- incompatible enables  
- invalid ALU operand configuration  

Behavior is undefined and must not occur.

---

## 10. Illegal and Reserved Encodings

This section defines the treatment of invalid, undefined, and reserved signal encodings.

These rules ensure that all control signals remain well-defined and that invalid configurations are explicitly identified.

---

### 10.1 Definitions

#### 10.1.1 Valid Encoding

A value explicitly defined in a signal’s encoding table.

Example:

```
ALU_OP = 00 (ADD) → valid
```

---

#### 10.1.2 Reserved Encoding

A value within the encoding space that is not currently assigned a meaning.

Example:

```
ALU_OP = 13 → reserved
```

---

#### 10.1.3 Illegal Encoding

Any encoding that violates:

- signal definitions  
- control interaction rules  
- operand constraints  

Examples:

```
ALU_B_SRC = NONE when ALU_OP = ADD
Multiple input sources active for a loaded register
```

---

### 10.2 General Rule

All signals must use only valid encodings.

Constraint:

```
For any signal S:
    S ∈ valid_encoding(S)
```

Any violation results in an invalid control word.

---

### 10.3 Reserved Encoding Usage

Reserved encodings are not defined and must not be used.

Constraint:

```
If encoding ∈ reserved:
    control word is invalid
```

Properties:

- Reserved encodings have no defined behavior  
- They must not be interpreted or inferred  
- They are available for future expansion  

---

### 10.4 Illegal Control Configurations

A control word is illegal if it violates any constraint defined in:

- Section 6 (Global Signal Constraints)  
- Section 8 (Bus Interaction Constraints)  
- Section 9 (Control Signal Interaction Rules)  

Examples:

```
Multiple IDB drivers active
Multiple input sources for a loaded register
Invalid ALU operand configuration
Conflicting enable signals (e.g., PC_LOAD and PC_INC)
```

---

### 10.5 Behavior on Illegal Encoding

Illegal encodings produce undefined behavior.

Constraint:

```
If control word is invalid:
    system behavior is undefined
```

This includes:

- incorrect state transitions  
- unpredictable datapath behavior  
- non-deterministic results  

No guarantees are made for:

- register contents  
- memory operations  
- control flow  

---

### 10.6 No Implicit Recovery

The system must not attempt to correct or reinterpret illegal encodings.

Constraints:

- No fallback behavior  
- No automatic correction  
- No default substitution of values  

All behavior must be explicitly defined.

---

### 10.7 Reserved vs Illegal Distinction

Reserved encodings are not inherently illegal, but:

```
Using a reserved encoding → illegal control word
```

Distinction:

- Reserved → unused but defined encoding space  
- Illegal → violation of system rules  

---

### 10.8 Completeness Requirement

All defined encodings must be listed explicitly in signal definitions.

Constraint:

```
No implicit or undocumented encodings are permitted
```

This ensures:

- full enumerability of signal behavior  
- no hidden or inferred states  

---

### 10.9 Design Guarantee

Valid control words guarantee deterministic execution.

Constraint:

```
If all signals use valid encodings and obey all constraints:
    system behavior is fully defined and deterministic
```

---

### 10.10 Summary

A control word is valid if and only if:

```
1. All signals use valid encodings
2. No reserved encoding is used
3. All interaction constraints are satisfied
4. Exactly one source drives each loaded destination
```

Any violation results in undefined behavior.

---

## 11. Timing Model

This section defines the timing behavior of control signals and datapath elements using the system timing primitives:

- TS (Timing State)
- TP (Timing Pulse)

This section is limited to temporal behavior. Functional behavior is defined in earlier sections.

---

### 11.1 Timing Primitives

#### 11.1.1 Timing State (TS)

A Timing State represents a discrete control step within instruction execution.

Properties:

- Control signals are defined per TS  
- Each TS produces exactly one control word  
- System behavior is fully determined by the active TS  

---

#### 11.1.2 Timing Pulse (TP)

TP is the commit event within a Timing State.

Properties:

- All register updates occur at TP  
- TP marks the boundary between consecutive TS values  
- TP is the only point at which architectural state changes  

---

### 11.2 Signal Stability Within TS

All signals must remain stable throughout the active Timing State.

Constraint:

```
During a TS:
    all control signals are constant
```

Implications:

- No signal may change between TS entry and TP  
- No mid-cycle control transitions are permitted  

---

### 11.3 Combinational Evaluation During TS

During each TS:

- Combinational logic evaluates continuously  
- All intermediate datapath values are produced  

This includes:

- ALU output  
- IDB value (if driven)  
- functional unit outputs  

Constraint:

```
All combinational outputs must be stable before TP
```

---

### 11.4 State Update at TP

State updates occur only at TP.

Constraint:

```
If R_LOAD = 1 during TS:
    R is updated at TP
```

Properties:

- All register updates occur simultaneously  
- No register updates occur outside TP  
- Updates reflect values computed during the same TS  

---

### 11.5 Pre-TS State Visibility

All datapath inputs within a TS are derived from:

- register values established at the previous TP  
- current combinational outputs  

Constraint:

```
All reads during TS observe:
    state from previous TP
```

---

### 11.6 No Intra-TS Feedback

A register must not depend on a value written in the same TS.

Constraint:

```
No datapath path may use:
    a value that is written at the current TP
    as an input within the same TS
```

Implication:

- All computations use pre-TP state  
- No combinational path may observe future state  

---

### 11.7 IDB Timing

IDB is valid only within the active Timing State.

Constraints:

```
If IDB_DRIVE = 1:
    IDB must be stable before TP
```

Properties:

- IDB has no state  
- IDB value is not retained across TS boundaries  

---

### 11.8 ALU Timing

ALU operates combinationally within TS.

Constraints:

```
ALU_RESULT must be stable before TP
```

Properties:

- ALU produces a result every TS  
- Result is used only if captured at TP  

---

### 11.9 External Timing (MDB and DB)

External data must align with TP.

Constraints:

#### Memory read:
```
MDB_INPUT must be valid before TP when MB_LOAD = 1
```

#### Memory write:
```
MB must be stable before TP when MEM_WR is asserted
```

#### I/O input:
```
DB_INPUT must be valid before it is sampled at TP
```

No implicit synchronization is provided.

---

### 11.10 Deterministic Timing Behavior

For any Timing State:

```
Given a control word and prior state:
    the resulting state at TP is fully determined
```

Requirements:

- stable signals during TS  
- stable combinational outputs before TP  
- single commit point at TP  

---

### 11.11 Invalid Timing Conditions

The following conditions are invalid:

- control signal transitions within a TS  
- unstable datapath inputs at TP  
- combinational outputs not settled before TP  

Behavior under these conditions is undefined.

---

## 12. Determinism and Completeness Guarantees

This section defines the global correctness properties of the control system.

A control word is valid only if it produces a fully specified, deterministic state transition consistent with all prior sections.

---

### 12.1 Determinism Guarantee

System behavior must be deterministic for all valid control words.

Constraint:

```
Given:
    - a control word for TS
    - system state at previous TP

The resulting system state at TP is uniquely determined.
```

Implications:

- No ambiguity in signal interpretation  
- No dependence on undefined or implicit values  
- No multiple possible outcomes for the same inputs  

---

### 12.2 Completeness Guarantee

All control words must fully specify system behavior.

Constraint:

```
For every TS:
    all signals are present
    all signals contain valid encodings
```

Implications:

- No “don’t care” states  
- No omitted signals  
- No partially defined control words  

---

### 12.3 Single-Result Guarantee

Each cycle produces a single coherent state transition.

Constraint:

```
At TP:
    all enabled state updates occur simultaneously
    all updates are consistent with a single control word
```

Implications:

- No partial state updates  
- No ordering ambiguity between register writes  
- No intermediate visible states  

---

### 12.4 Single-Source Guarantee

All data movement is unambiguous.

Constraint:

```
For any register R:
    if R_LOAD = 1:
        exactly one input source determines R_INPUT
```

Implications:

- No multiple drivers  
- No conflicting data sources  
- No undefined input values  

---

### 12.5 Signal Independence Guarantee

Signal classes remain independent.

Constraint:

```
Enable signals do not imply:
    - data source selection
    - operation selection

Select signals do not imply:
    - enable behavior

Data Value signals do not imply:
    - selection or enable
```

Implications:

- All behavior is explicitly constructed  
- No hidden coupling between signals  

---

### 12.6 Domain Isolation Guarantee

Data transport domains remain independent and correctly composed.

Constraint:

```
All domain interactions:
    - occur only through defined mechanisms
    - obey domain constraints (Section 8)
```

Implications:

- No unintended cross-domain behavior  
- No implicit routing between domains  

---

### 12.7 Timing Determinism Guarantee

Timing behavior is fully defined.

Constraint:

```
Within each TS:
    - all signals are stable
    - all combinational outputs settle before TP

At TP:
    - all state updates occur atomically
```

Implications:

- No race conditions  
- No timing-dependent ambiguity  
- No partial evaluation effects  

---

### 12.8 Valid Control Word Definition

A control word is valid if and only if:

```
1. All signals use valid encodings
2. No reserved encodings are used
3. All interaction constraints are satisfied
4. Exactly one source drives each loaded destination
5. All domain rules are followed
6. Timing constraints are satisfied
```

---

### 12.9 Invalid Control Word Behavior

Any violation of these guarantees results in an invalid control word.

Constraint:

```
If any guarantee is violated:
    system behavior is undefined
```

Implications:

- No recovery mechanisms are defined  
- No fallback behavior exists  
- Invalid states must not occur in correct operation  

---

### 12.10 Final Guarantee

For all valid control words:

```
System behavior is:
    - fully specified
    - deterministic
    - temporally consistent
    - free of ambiguity
```

This ensures that the control system provides a complete and correct mapping from control words to state transitions.
